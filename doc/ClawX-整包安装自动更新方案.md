# ClawX 整包安装自动更新方案

## 1. 结论

可以复用。

ClawX 当前已经有一套可工作的 `electron-updater` 链路，而且不是只有一半，主进程、渲染层设置页、打包配置、发布工作流、OSS 更新清单上传都已经具备基础能力。

如果你的目标是：

- 最小改动
- 不大拆当前架构
- 接受“下载完整安装包并覆盖升级”
- 不追求把 TS/TSX 与 GUI 完全外置

那么优先走“整包安装自动更新”是完全合理的。

这条路线的优点是：

- 代码改动最小
- 风险最低
- 能最快落地
- 不需要重做启动架构
- 不需要重写打包链路
- 不容易出现热更新混版本导致的函数缺失

## 2. 当前 ClawX 已经具备的基础

### 2.1 主进程更新能力已存在

当前 ClawX 已有：

- `electron/main/updater.ts`
- `autoUpdater.checkForUpdates()`
- `autoUpdater.downloadUpdate()`
- `autoUpdater.quitAndInstall()`
- IPC 通道：
  - `update:status`
  - `update:version`
  - `update:check`
  - `update:download`
  - `update:install`

### 2.2 前端设置页已存在

当前设置页已经有完整更新 UI：

- 当前版本展示
- 手动检查更新
- 下载更新
- 安装更新
- 自动检查更新开关
- 自动下载更新开关

也就是说，从用户视角看，ClawX 已经接近一个可用的自动更新产品形态了。

### 2.3 打包配置已存在

当前 `electron-builder.yml` 已配置：

- `publish.generic`
- `publish.github`
- `win.verifyUpdateCodeSignature: false`
- Windows 目标为 `nsis`

这意味着 `electron-builder` 会生成整包安装升级需要的核心文件：

- Windows 安装包 `.exe`
- 更新元数据 `.yml`
- blockmap 文件

### 2.4 发布工作流也已存在

当前 GitHub Actions 已包含：

- Windows 打包
- 生成和修正 `latest.yml` / channel yml
- 上传 GitHub Release
- 上传 OSS 的 channel 目录

这套链路已经非常接近“直接可用”。

## 3. 这条方案怎么更新

这里说的是“用户怎么更新”和“你作为发布者怎么发更新”。

### 3.1 用户侧更新流程

用户安装的是正常的 ClawX 安装包。

后续更新时，流程是：

1. 用户打开 ClawX。
2. 应用启动后自动检查更新，或者用户在设置页点“检查更新”。
3. `electron-updater` 从配置的更新源下载新的整包安装文件和元数据。
4. 下载完成后，用户点击“安装并重启”，或者自动倒计时安装。
5. 应用退出，安装器执行升级。
6. 新版本覆盖旧版本安装目录。
7. 用户数据目录保留，应用升级完成。

对用户来说，体验上仍然是“应用内更新”，只是底层拿到的是完整安装包。

### 3.2 发布者侧更新流程

你后续每次发版时，流程应为：

1. 修改 `package.json` 版本号。
2. 打 Windows 包。
3. 生成 `.exe`、`.yml`、`.blockmap`。
4. 上传到 OSS 对应 channel 目录。
5. 或同步上传到 GitHub Release。
6. 用户端下次检查更新时，就会拿到新版本。

也就是说，你不需要额外维护 zip 热更新包，只需要继续发标准安装包。

## 4. 为什么这条路线是“最小改动”

因为当前 ClawX 已经在用这套东西了，真正需要补的不是重构，而是“把它做完整、做稳定、做清楚”。

最小改动的核心是：

### 4.1 不动启动架构

不用做：

- Shell / Runtime 分层
- 外置 `main/preload/renderer` 运行时
- 动态版本目录切换
- 启动健康检查回滚系统

这意味着不用大改：

- `electron/main/index.ts`
- `BrowserWindow` 加载方式
- `vite.config.ts`
- 现有构建产物组织结构

### 4.2 不动页面与业务代码承载方式

你现在的 TS、TSX、主进程逻辑仍然跟随完整安装包发布。

这虽然不像“外置 Runtime”那样灵活，但它有一个很大的现实优势：

- 每次升级时，主进程、Preload、Renderer 一定是同一个打包版本

所以它天然规避了“函数找不到”的主要来源。

### 4.3 不动现有 CI/CD 主路线

当前仓库已经有：

- `release.yml`
- `package-win-manual.yml`

这意味着发布侧的骨架已经在，不需要从零搭建更新发布平台。

## 5. 这条方案的核心原理

整包自动更新的本质不是“下载页面资源”，而是：

- 下载完整新版本安装包
- 通过安装器替换旧应用
- 保留用户数据目录

这条路线为什么更稳：

- 新版本是完整包，不存在某些目录只替换一半
- 主进程和页面代码天然同版本
- 不会留下旧版 `dist` 和新版 `preload` 混合的问题
- 一次升级就是一个完整应用快照

对于你现在最关心的“最小改动”和“先快速可用”，这是更合适的。

## 6. 当前方案里你真正需要关心的几个点

### 6.1 更新源地址

当前 ClawX 已经配置了默认 OSS 更新源：

- `https://oss.intelli-spectrum.com/latest`

并且支持 channel：

- `latest`
- `alpha`
- `beta`

如果你后面要换成自己的下载地址，有两种做法：

1. 继续沿用当前 OSS 结构，只是把文件上传到你的目录。
2. 改 `electron-builder.yml` 和 `updater.ts` 里的 feed URL，切到你的域名。

对整包方案来说，这个改动很小。

### 6.2 只在打包后可测试

`electron-updater` 在开发模式下不会正常执行升级。

所以这条路线的一个现实要求是：

- 必须在打包后的应用里测试

开发态只能测 UI，不适合测真正的升级安装。

### 6.3 版本号必须规范

必须保证每次发布版本递增，例如：

- `0.3.8`
- `0.3.9`
- `0.4.0`

如果版本号不变，客户端不会认为有新版本。

### 6.4 更新元数据必须与最终安装包一致

这是整包方案最容易踩坑的地方之一。

因为 Windows 包如果在打包后又经过签名，`.exe` 的 hash 会变。

当前仓库里的发布工作流已经专门处理了这个问题：

- 签名后重新写回 `.yml` 中的 `sha512`

所以这部分应继续保留，不能删。

## 7. 我建议的“最小改动整包方案”

这条方案建议尽量复用现有实现，只做有限增强。

### 7.1 第一阶段：确认并固化现有链路

目标：

- 不做架构重构
- 先把现有 `electron-updater` 链路当成正式主方案

建议动作：

1. 明确 Windows 作为首发平台。
2. 明确稳定更新源地址。
3. 固定版本号发布规范。
4. 用一条完整链路实测一次：
   - 旧版本安装
   - 发布新版本
   - 检查更新
   - 下载
   - 安装重启
   - 验证用户数据保留

### 7.2 第二阶段：补配置与日志

目标：

- 让线上问题可查

建议补充：

- 更新源地址日志
- 当前 channel 日志
- 当前版本 / 远端版本日志
- 下载失败错误信息
- 安装触发时间
- 升级后首次启动日志

这一步改动很小，但很值。

### 7.3 第三阶段：补产品化细节

目标：

- 提升用户体验

建议补充：

- 设置页中更明确的更新说明
- “下载完成后重启安装”的提示
- 更新失败后的帮助文案
- 可选的“跳过此版本”
- 可选的“查看更新日志”

这些都属于小改动，不会动主架构。

## 8. 这条方案下，我怎么发版本

如果采用整包方案，你后续发版本可以按这个模型做。

### 8.1 本地或 CI 打包

Windows：

- 运行 `pnpm run package:win`

如果要批量变体：

- 运行 `pnpm run package:win:variants`

### 8.2 产物

最终应至少有：

- `ClawX-xxx-win-x64.exe`
- `latest.yml` 或对应 channel 的 yml
- `.blockmap`

### 8.3 上传位置

如果走当前默认方案，应上传到：

- `https://oss.intelli-spectrum.com/latest`

或其它 channel 目录：

- `https://oss.intelli-spectrum.com/alpha`
- `https://oss.intelli-spectrum.com/beta`

### 8.4 用户端触发

用户端不需要重新下载安装包。

用户只需要：

1. 打开 ClawX
2. 等自动检查，或手动点检查更新
3. 下载并安装

## 9. 这条方案下，我怎么给你提供下载地址

如果你要切成你自己的地址，推荐按 `electron-updater` 的标准结构提供，而不是只给一个孤立的 exe 下载链接。

也就是说，一个版本目录里至少应有：

- 安装包 `.exe`
- 更新清单 `.yml`
- blockmap

如果只有一个 exe 地址，没有对应 yml，`electron-updater` 不好正常工作。

所以整包方案下，你最好后续提供的是：

- 一个稳定的更新目录 URL

而不是：

- 单个文件 URL

## 10. 这条路线相比外置 Runtime 的优缺点

### 10.1 优点

- 最小改动
- 落地最快
- 风险最低
- 架构不用大改
- 不容易出现函数缺失
- 与当前 ClawX 实现最贴近

### 10.2 缺点

- 每次都下载整包，体积更大
- 更新速度可能慢一些
- 页面小改动也要发整包
- 不能做到只更新 TS/TSX 所对应的业务层
- 以后如果想做更细粒度热更新，还得再升级架构

## 11. 我对 ClawX 的建议

如果从“先把功能做出来”的角度，我建议：

### 建议一

先正式采用“整包自动更新”作为第一阶段主方案。

理由：

- 当前仓库已经有 70% 到 85% 的基础
- 改动少
- 可以尽快上线

### 建议二

把“外置 Runtime 更新”作为第二阶段增强方案，而不是第一阶段必做项。

理由：

- 外置 Runtime 架构改动太大
- 当前项目还有很多主线功能在推进
- 先用整包方案把更新闭环跑通更实际

### 建议三

先把 Windows 跑通，其他平台后补。

理由：

- 你当前重点就是 Windows
- NSIS + electron-updater 在 Windows 上路径最清晰

## 12. 首版实施范围建议

如果按最小改动推进，我建议首版只做下面这些：

1. 保留当前 `electron-updater`
2. 固化 OSS 更新源
3. 完整实测 Windows 升级链路
4. 补日志与错误提示
5. 视情况补一个“查看更新日志”入口

首版先不要做：

- 不做外置 Runtime
- 不做 zip 热更新
- 不做双更新体系并行切换
- 不做复杂回滚器

## 13. 实施前确认项

如果你准备走整包方案，我建议你先确认这 5 项：

1. 是否先只做 Windows。
2. 是否继续复用当前 `electron-updater` 作为主更新机制。
3. 是否继续复用当前 OSS / GitHub Release 的发布结构。
4. 你后续提供的是“更新目录地址”还是“单文件下载地址”。
5. 首版是否接受“下载完整安装包并重启安装”的体验。

## 14. 最终结论

当前 ClawX 的 `electron-updater` 完全值得复用，而且从实际工程角度看，它就是现在最适合做“最小改动自动更新”的方案。

如果你现在优先级是：

- 先可用
- 先稳定
- 先少改代码

那我建议下一步就按这条整包方案推进，不先上外置 Runtime 架构。

等整包更新稳定后，再决定要不要演进到“外置 Runtime + 资源包更新”这条更重的路线。
